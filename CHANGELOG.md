# Changelog

All notable Swarm release changes should be recorded here.

Release entries are the source checkpoint for public docs verification. Each entry must include a `Docs impact` section. If a release has no docs-impacting changes, write `Docs impact: none`.

## Unreleased
- Swarm never changes the machine it runs on. The headless installer gains `install.sh workspace add PATH | remove PATH | list`: run as root by the person or by the AI setting the machine up, `add` makes exactly that Git repository (in a person's home, owned by them) visible and writable to Swarm and its agent sandboxes at its real path (a unit drop-in with `ProtectHome=tmpfs` and `BindPaths=`, access for Swarm's user on that folder only, default ACLs so the owner keeps full rights on what Swarm creates) and restarts Swarm; `remove` reverses it; `uninstall` revokes every folder. `POST /v1/workspace/add` (and `swarm_add_workspace`) answers a path Swarm cannot see with `409 workspace_not_visible` naming that command instead of "no such directory". In the sandbox, each project's `.git/hooks` and `.git/config` are mounted read-only, and Git is told the project root is safe (`safe.directory`) when another user owns it. Docs impact: headless README, setup and using-swarm skills.
- AI onboarding over Swarm Control now builds a real project instead of an empty repository: the server instructions tell the AI to ask which existing folders or repositories to add, register them with the new `swarm_add_workspace` (refuses empty folders, system and Swarm storage directories and folders inside a registered workspace; changes nothing in the folder), group them with `swarm_create_project` (workspaces by path or id with a role), wait with the new `swarm_get_project` until the generated `project.md` is ready, then work through the project's orchestrator. New `swarm_update_project_context`, `swarm_set_project_workspaces` and `swarm_retry_project_context` edit `project.md`, replace the workspace list and rerun a failed generation (edits are refused, with the next step, until generation is ready). `swarm_create_workspace` is described as a new, empty repository for a project started from scratch and is no longer suggested by errors. `/v1/workspace/add` accepts `require_existing_content` with `context_only`. The SDK drops `projects.synthesizeContext()`, which called a retired route (HTTP 410); `retryContext` reruns generation. Docs impact: Swarm plugin skills (using-swarm, setup, building-on-swarm), SDK README projects section, headless and application image READMEs, Swarm Control and project orchestrator checkpoints.
- Add the `claudecode` provider, which runs the locally installed, unmodified Claude Code CLI the person signed into themselves (no Claude credentials handled by Swarm). It is enabled per account through a secret-free CLI credential, runs with built-in tools and user settings removed, and executes only Swarm tools through a token-guarded loopback MCP bridge under Swarm permissions. Docs impact: `docs/checkpoints/claude-code-provider.md` documents setup and isolation.
- Claude Code provider: Opus 4.6 and Sonnet 4.6 run with a 200k window in Claude Code unless the 1M variant is named, while Swarm compacted against the catalog's 1M, so long conversations failed before Swarm compacted; the provider now asks Claude Code for the `[1m]` variant whenever the catalog window is larger than 200k (usage still names the catalog model). New `/claude` command in the terminal UI and `GET /v1/claudecode/usage`: Claude Code version, sign-in and plan, and the latest five-hour and weekly usage Claude Code reported in a turn (known after the first Claude Code turn since the daemon started; no credentials read). Docs impact: `docs/checkpoints/claude-code-provider.md`.
- The headless image no longer carries `/usr/bin/pebble`, a binary the Ubuntu 26.04 base image ships outside any package (so upgrades never patch it). Swarm does not use it, and its Go 1.26.7 build has HIGH standard library CVEs that fail the release image scan. Docs impact: none.
- The release image check expects the headless image's real entrypoint (`swarmd --desktop-port=0 --cwd=/project --lock-permission-policy`). The startup lock flag was added to the image but not to the check, so the release stopped after building the image. A test now ties the check to the Dockerfile. Docs impact: none.
- The installer works unattended, the way an AI runs it. With no terminal (`curl -fsSL https://swarmagent.dev/install | sh -s -- --yes`), it now starts the service when systemd is running (`--no-service` otherwise) and says which it chose; before, the terminal check passed on file permissions, the read failed, and the empty answer meant files only, so Swarm was never started and nothing said so. Without `--yes` and no terminal it stops with the rerun line instead of "install cancelled". A non-root run with no terminal checks `sudo -n true` first and, if sudo needs a password, stops before changing anything with the exact command to run. `curl … | sudo sh -s -- --yes` installs for the sudo user instead of a separate `swarm` service account, so that person's AI can use `swarm mcp`; direct root still creates the service account and explicit account flags still win. The installer prints the Claude Code, Codex and owner setup lines at the end of every install, and the whole script runs only once fully downloaded. The distro install test now really runs its sudo scenario (its commands never reached the container before) and adds an unattended non-root install that checks the service, the owner and `swarm mcp` answering `tools/list`. Docs impact: README install and Connect your AI.
- `swarm ctl setup …` works: the launcher appended `--addr`, which `swarmctl setup` rejects because setup only talks to the owner socket. On a brand-new Swarm, `swarm mcp` tool calls now answer "Swarm has no owner yet" with the exact `swarm ctl setup identity --username … --name …` command instead of "Swarm refused to give this user an AI key (HTTP 401): trusted principal required". Docs impact: setup skill.
- The Claude Code / Codex plugin launcher (`plugins/swarm/bin/swarm-mcp`) uses `swarm mcp` only when the installed Swarm has it (an older `swarm` opened the terminal UI on the MCP connection), falls back to `swarmctl` on PATH or in `/usr/local/share/swarm/bin`, and otherwise says to update Swarm, with nothing written to the MCP stream. Docs impact: plugin README and setup skill.
- SDK: `new SwarmClient()` with no options connects to the local Swarm: `SWARM_SOCKET_PATH`, then `SWARM_API_URL` / `SWARM_DESKTOP_URL`, then (Node) the owner socket `/var/lib/swarmd/local-transport/api.sock` when this process can use it, then `http://127.0.0.1:7781`. It used `http://127.0.0.1:18080`, where Swarm never listens. An explicit `baseUrl` now wins over `SWARM_SOCKET_PATH`. Docs impact: SDK README (one socket path, `npm install @swarm-agent/sdk`, Node 22+).
- New release-gate test `scripts/e2e/ai-path.mjs`: five independent scenarios (onboard, chat, tasks, sdk, restart), each on its own fresh daemon, drive Swarm the way an AI does (MCP over `swarmctl mcp`, the provider key page, the npm SDK) with a real model. Docs impact: none.
- Test cleanup, no product change: removed the tooling for the retired remote testbench (the `run-testbench-*` wrappers, `ssh-fast-test`, `swarm-harness-vm`, the launch prerun suite, the local testbench pool, tunnels, deploy and model-config scripts, the `testbench-codex-broker` command and their tests) and the 17 relocated Go test packages under `tests/` that no longer compiled. Live candidate testing runs in the release pipeline. Docs impact: README, AGENTS.md and web/README testing instructions.
- Default tool permissions audited (`docs/permissions-defaults.md`). A `manage_projects` `propose_task`/`create_task` whose card waits for Approve no longer asks when it has no title or no source: the small Router call that names it or picks the source is accepted cost, and the card stays the gate. `approve_task`, `accept_task`, `deploy_task`, proposals that start work or spend at once (`auto_approve`, plan agent, media), `delete`, `delete_task` and `archive_task` now have their own permission identities (`project_task_launch`, `project_removal`): the Orchestrator's enabled `manage_projects` tool compiles to an allow rule that used to pre-approve them, so the Orchestrator could approve or deploy its own task cards and delete projects without a prompt. They now ask; a saved deny for `manage_projects` still blocks them, and "always allow" from their prompt saves a rule for that identity only. Docs impact: docs/permissions-defaults.md.
- Conversations get a title without a model call: when the first user message reaches a session or project conversation whose title is still a placeholder (empty, "New Session", or the old SDK defaults "Orchestrator AI" and "Chat Session"), Swarm titles it from that message's first line (Markdown markers and extra spaces removed, at most 60 characters) before the message request returns, so `listConversations` and session lists show it at once. The existing Compact/Router title model can still replace this provisional title; a title the client gave is never replaced. `POST /v3/sessions/{id}/title` (owner only, already used by the desktop) renames and locks a title. SDK: new `sessions.rename(id, title)` and `projects.renameConversation(id, title)`; `projects.createConversation` and `chat.createSession` no longer send the placeholder titles that kept Swarm from titling conversations. Docs impact: SDK README projects section.
- SDK turns Swarm's `<copy label="…">…</copy>` snippet tags (a desktop/terminal copy-button convention in agent replies) into Markdown code blocks by default in `chat.run`, `chat.listMessages` and `chat.stream` (`onText` stays append-only while streaming, `onComplete`), and so in the browser chat bridge; `rawCopyTags: true` keeps them. New exported `copyTagsToMarkdown(text, { streaming })` and `hasCopyTags(text)` for text read elsewhere. Agent prompts and stored messages are unchanged, so Swarm's own apps keep their copy buttons. Docs impact: SDK README projects section.
- A finished command that printed nothing now records `output: ""` instead of no output (which apps read as `null`) in its durable `session.tool.completed` / `failed` / `cancelled` event, and the event carries the command's `exit_code` when the tool reports one (bash, git tools). Docs impact: none.
- A brand-new Swarm now reports `config.desktop_onboarding_complete: false` from `GET /v1/onboarding`. The daemon wrote its first startup config from the legacy default `true` (meant for config files that predate the key), so a fresh Swarm with no identity reported onboarding complete. Config files without the key still count as complete. Docs impact: none.
- The orchestrator's per-turn "Recent Project Tasks & Deliverables" context now lists the project's 10 newest tasks; it listed the 10 oldest, so in projects with more than 10 tasks the newest work was missing. Only those 10 tasks are hydrated per turn instead of every task in the project. Docs impact: none.
- Fewer approval prompts for reads and task cards under the default permissions. `manage_projects` `propose_task`/`create_task` no longer ask when the created card waits in `pending_approval`, because the card's Approve is the gate: that needs `auto_approve` absent or false, agent `coder`, `swarm` or `finder` (or intent `code`/`audit`) and no media `operation`. Auto-approved, plan-agent and media tasks still ask. `manage_projects` `inspect_files` (one read/list/search/find inside an authorized source or exact task result) is now a read. Single bash commands declared `read` also run without approval for `echo`/`printf` with plain arguments, `git branch` listing, `git worktree list`, `git rev-parse`, `git ls-files`, `git remote [-v]`, `git show-ref`, `git describe` and `git blame`. `ls`, `wc`, `cat`, `head`, `tail`, `stat`, `file`, `grep`, `rg`, `tree` and `du` run without approval only in V3 runs, and only when the session's cwd and every path resolve (symlinks followed) to an existing file or directory inside the session's workspace roots. Each command accepts only an allowlist of options: following symlinks, file lists or patterns read from other files, helper programs, output files and `tail -f` all still ask, as do globs, `~`, `workspace_path` and `/proc`, `/sys` and `/dev`. `ls` used to be allowed with any path; it now follows the same rule. `ls -l`, `wc -l`, `grep -l` and `tree -L` are no longer flagged as network listeners. `ps`, `history`, `env`, writes and account memory changes still ask, and explicit rules plus the read/readwrite execution settings still win. Docs impact: none.
- SDK `projects.integrateTask(projectId, taskId)` now works with no extra arguments. It posted an empty body, which the daemon refuses with "select the task session and target branch before integrating: EOF"; it now reads the task (`getTask`) and sends the selection the daemon checks: `session_id` (the task's current session) and the captured `source_branch` / `target_branch` (from `task.delivery_assessment`, else the task's `worktree_branch` / `base_branch`, else its active attempt), plus `revision`, `attempt_id` and the observed `source_head` / `target_head`. Callers can override any field with `options.selection`; a full `session_id` + branches selection skips the read. A task with no captured worktree lane throws `SwarmValidationError` without calling the daemon. `ProjectTaskRecord` gains `active_attempt_id`, `attempts` and `delivery_assessment`. Covered by hermetic SDK tests only. Docs impact: SDK README projects section.
- SDK live tool objects (`chat.stream` `onToolStarted/onToolDelta/onToolCompleted`, browser chat `tool_start/tool_delta/tool_done`) gain `callId`, equal to `payload.call_id` on the durable `session.tool.*` events, so apps can merge history and live tool cards without showing each tool twice; `id` is unchanged. A lifecycle event that carries only `tool_instance_id` (`step-<n>:<call_id>`) now resolves to the same tool. Docs impact: SDK README chat and browser examples match on `callId`.
- SDK chat streams and `realtime.watchSession` keep a conversation openable after a very large tool result: when `/v3/sync/hydrate` refuses with `requires_manifest` (the newest history no longer fits the 256 KB window), the watch retries once with `history.manifest_policy: 'manifest'`, which returns the same newest window, and keeps that policy for later hydrations. `state.historyOmitted` and `state.historyOmissions` (resource and `next_cursor`) say that older history was left out. Other hydrate errors still fail the watch. Covered by hermetic SDK tests only. Docs impact: SDK README streaming guarantees.
- SDK `describePermission(p).title` is never empty: without a title in the request it falls back to the bash command, the first ask-user question, or the humanized tool name and action (for example `Manage projects: propose task (Add login)`), as one line of plain text capped at 160 characters. Docs impact: SDK README permissions section.
- A finished tool call's durable `session.tool.completed` / `session.tool.failed` event now carries what the tool produced in `payload.output` (a command's stdout, a tool's result; bounded to 128 KiB like the tool result the model sees, with `output_truncated` and `output_bytes` when cut), so an app that rebuilds tool cards from durable events after a reload can show what a command printed. The completion label that used to be there (for example "bash date +%s") moves to `payload.summary`; `raw_output` is unchanged. Docs impact: none.
- Project tasks now notify the person: when a task (an orchestrated task or the task a worker run executes) reaches `needs_review`, `failed` or `completed`, `GET /v1/notifications` gains one notification of category `task` ("Task ready for review: <title>", "Task failed: <title>", "Task completed: <title>") carrying the project, task, attempt and session ids in `payload`. Each task attempt notifies at most once per status: rewrites of the same status, retries and replays add nothing. Docs impact: none.
- A client tool whose app reports an error (SDK `ClientToolError('Order not found')`, or a client tool timeout) is now a tool failure with the app's message: the model gets a tool error instead of a permission denial, the session records `session.tool.failed` with that message, and no "Permission denied: Lookup order" notification is raised. Client tool calls no longer create permission notifications or agent-blocked signals at all, because the app answers them, not a person. Docs impact: none.
- The owner's name is kept as typed: `onboarding.ensureBootstrapped({ username: 'Grader', ... })` now reports `identity.username` "Grader" (also in `/v1/me`, the desktop session and the account rename reply); only the internal unique handle is lower-cased. Sending the name already set again (any letter case) through `POST /v1/onboarding`, with or without the same `swarm_name`, now succeeds without changing anything instead of failing 409 "identity bootstrap already exists"; a different name still answers 409, now with "the owner name is already set to "Grader"; change it in account settings instead", because renaming belongs to the account route. Docs impact: none.
- `onboarding.ensureBootstrapped` only creates the identity: it no longer marks onboarding finished, so `config.desktop_onboarding_complete` stays false until the app or the desktop finishes setup (the desktop and `swarmctl setup complete` already set it at their own finish step), and calling it on a bootstrapped Swarm sends nothing. Docs impact: SDK `HEADLESS_UI.md` explains when to call `update({ desktop_onboarding_complete: true })`.
- A finished project task whose work is committed on its branch can be integrated when the source workspace only holds untracked files the task does not write, such as an app's own state files: `GET /v3/projects/{id}/tasks/{task}` offers `integrate` and `POST .../integrate` leaves those files untouched. Tracked changes, untracked files the task would overwrite, and anything uncommitted in the task worktree still block, and the message now names the files (for example `Target checkout on "main" has uncommitted changes: base (modified)`) instead of "Source or target has uncommitted changes"; the assessment carries them as `source_dirty_files` / `target_dirty_files`. A refusal for uncommitted changes no longer records a failed integration attempt. Docs impact: none.
- SDK `SwarmBrowserChat.sendMessage` refusals now throw `SwarmChatNotReadyError` with a message fit to show people and a `code`: `chat_reconnecting` ("Not sent: reconnecting to Swarm, try again in a moment", `retryable: true`), `chat_disconnected` or `chat_not_subscribed`, instead of "Await subscribe(sessionId) before sending". Docs impact: SDK README browser chat notes.
- A custom agent defined without a model of its own (for example an SDK sealed agent from `agents.defineSealedAgent` with only a prompt and client tools) now runs on the account's default Swarm model, the same one a plain session gets; before, its first message failed with "resolved v3 provider/model is empty". A model set on the agent still wins. If no model was ever set up, the run fails with "no model is set up yet". Docs impact: none.
- Creating a session without `workspace_path` on a Swarm with no current workspace now fails with a plain error ("this session needs a workspace: pass workspace_path of a registered workspace") instead of "sessions v3 primary account has no default workspace". Sessions, sealed agents' included, stay bound to a workspace. Docs impact: none.
- `GET /v1/agent-model-settings` on a Swarm where no models were ever set up answers 200 with every role unset (`updated_at` 0) and the role list, instead of a 404 "agent model settings not found" that apps showed as an error during onboarding. SDK `settings.agentModels()` returns that empty record. Docs impact: none.
- Clearing a conversation's context now also stops its agent from reading the cleared history back through its tools: `manage_sessions` `read_messages`, session-scoped `search` and `durable_log` search (and `manage_agent` transcripts) on the agent's own session stop at the clear. The person and the UI still see the full history, and reads of other sessions are unchanged. Docs impact: none.
- Read-only `manage_projects` actions (`list`, `get`, `list_sources`, `inspect_source`, `list_media`, `get_media`, `list_tasks`, `get_task`) no longer ask for approval under the default permissions; every other action still does, and explicit deny rules still apply. `manage_sessions` reads were already approval-free. Docs impact: none.
- Provider status text no longer points at one client's UI: a missing Exa key reads "no Exa API key yet" (web tools: "no Exa API key is set up yet") instead of "add one in Settings > Providers or run /auth key exa", and the Copilot status no longer says "until changed in /auth", since the same text reaches SDK apps and MCP clients. Docs impact: none.
- A project chat's `bash` in a project that has no workspace yet now fails with "this project has no workspace yet: add a workspace to the project to run commands" instead of "recovery repository is not in the account workspace catalog". Docs impact: none.
- Swarm Control can take work from zero to a reviewed result without the Desktop. New tools: `swarm_approve_task` (manage level) approves or rejects a `pending_approval` project task through the Desktop's own route and guards; `swarm_accept_review` (approve level) accepts the checkpoint a `waiting_review` plan is waiting on; `swarm_get_changes` and `swarm_read_file` (read level) show a session's commits, changed and untracked files and diff against its worktree base, and read one text file (256 KiB cap) inside that worktree or a registered workspace, refusing `..`, absolute paths, symlink escape, `.git`, `.env*`, binary files and Swarm's protected storage. `start_session`, `send_message` and `run_plan` now return the start ids plus one session read made afterwards instead of contradictory snapshots; `wait_seconds` allows up to 110 seconds and reports how the run settled (`finished`, `failed`, `stopped`, or `waiting_on_decision`); `stop_run` reports the run's final status and that a stopped plan is paused, not cancelled; pending requests carry decoded `tool_arguments` and the canonical `ask_user` name; `get_session` takes `detail_chars` for full tool output; usage explains zero cost (`billing`: `subscription`, `metered` or `unpriced`) and shows unset limits as `none`; `list_providers` shows a working sign-in as `signed in` and can wait for a requested key; an unregistered `workspace_path` and unknown ids get errors naming the right list tool; server instructions mention only tools the caller's level allows and that policy-refused commands never become approval requests. Docs impact: `docs/checkpoints/swarm-control.md` tool table, wait semantics and review flow updated.
- Daemon fixes from driving Swarm through Swarm Control. `plan_manage`'s `recommendation` schema now advertises the exact accepted `decision` and `action_state` values (`taken`, `ready`, `needs_approval`) and rejections list them, so a first `complete_checkpoint` or `mark_blocked` call no longer guesses. `manage_projects inspect_files` accepts `inspection`/`inspection.arguments` sent as a JSON-encoded object. Repository setup (`POST /v1/workspace/repository/setup`) writes a repository-local `Swarm agent` committer identity when none is configured (global config is never touched), and refuses relative paths, system directories (`/etc`, `/usr`, `/proc`, ...), Swarm's storage roots and folders inside a registered workspace before creating anything. Activating a worker, or admitting a new worker run, whose workspace belongs to no project now fails at once with an error naming the fix, and no failed run is stored, so a same-key retry after the fix starts the run. Worker run reads carry a `review` object (`state: awaiting_review`, project and task ids, next action) while the run's task awaits review; run `status` keeps its meaning. A refused task integration names the delivery state and the action that resolves it (for example commit the worktree's uncommitted changes, or use `recover-integrate`) and returns the `delivery` assessment. A plan paused by a user run stop records `stopped_by: "user"` on the attempt and in the plan's execution summary. Single read-only `git status|log|diff|show`, `pwd` and `date` commands declared `read` run without approval in auto and plan modes; the built-in `cd`/`ls` allow no longer covers chained, piped, redirected or substituted commands. Docs impact: none.
- SDK chat streaming survives dropped connections without losing or repeating text. Joining or reconnecting mid-turn no longer tears the socket down when live output is ahead of durable checkpoints (it reconnected into the same gap until the watch died); the gap is held until the next checkpoint fills it. `onText` deltas now concatenate to exactly the assistant text across reconnects and include any committed tail, the reconnect budget applies per outage instead of per watch, socket events reach `state` immediately instead of only through re-hydration (which no longer runs for every token checkpoint), `onReasoning` fires from reasoning checkpoints, cancelled tools complete, and `onComplete(messages, run)` (and the bridge's `done`) carry the run status so failed turns are distinguishable. New `sessions.clearContext()`; the daemon now wakes realtime subscribers when context is cleared (it was delivered up to 15s late) and answers 409 instead of 500 for a standalone session. Proven by an opt-in end-to-end test of the built SDK against the API server with a scripted provider (`SWARM_SDK_E2E=1 go test ./internal/api -run TestSDKChatStreamE2E`); no real model was used. Docs impact: SDK README streaming section and `HEADLESS_UI.md` reconnect notes rewritten.
- A local AI client connects to Swarm with one line and no key to make: `claude mcp add swarm -- swarm mcp` (Claude Desktop and Codex CLI take the same command). `swarm mcp` (or `swarmctl mcp`, e.g. through `docker exec -i` for the headless container) is a stdio MCP bridge that forwards every message unchanged to Swarm Control (`/mcp`) over the daemon's owner socket. It runs only as the non-root user that owns that socket, who already has owner access, and never hands the AI owner authority: it mints a 30-minute AI key at `--access full` (default), `write` or `read`, keeps it only in memory, renews it while the client runs, and deletes every key it minted on exit; a key Swarm refuses stops the bridge rather than being replaced. stdout carries only MCP; a stopped Swarm or a wrong user is reported on stderr. The installer's closing message shows the Claude Code line. Docs impact: README gains "Connect your AI"; `docs/checkpoints/swarm-control.md` documents the bridge, client setups and trust boundary.
- An AI on Swarm Control can set or replace a provider API key without seeing it. `swarm_list_providers` (read) shows each provider's stored credential count, the active one's verification and the outcome of the latest key link, never key material. `swarm_request_provider_key` (manage, needs `admin`, not offered over the relay) returns a one-time link, valid 10 minutes, to a key page served only on the loopback API listener; the person pastes the key there, and it is saved, verified and made active through the canonical credential route as the requesting key. The page refuses cross-origin posts, proxied or non-loopback requests and reused or expired codes, and keeps the key out of every response. Docs impact: `docs/checkpoints/swarm-control.md` lists the tools and the page's boundaries.
- Workers can hand back X posts for review: an automation's deliverable requirement of kind `social_post` carries an operator-set action contract (only `publish_x_post` with `env:TWITTER`, no target URL or parameters; other kinds take no contract), and each completed run turns the final checkpoint result `{"tweet_text": "..."}` (only that field, non-empty, at most 280 characters, no control characters but newlines) into a `pending_review` `social_post` deliverable with that contract, so the agent chooses only the text. The run tells the agent the result format; an invalid required post fails the run with the reason and saves nothing, and repeated observation never duplicates a deliverable. Approving it (`POST /v3/deliverables/{id}/approve`) publishes as before. Docs impact: none.
- The headless installer follows `main`, the released build, by default (the documented install line and `--ref` default were `dev`, so new installs auto-updated from development every five minutes). `install.sh channel [BRANCH]` shows or switches the followed branch without reinstalling, and the update timer now only moves forward: a branch that does not contain the running build (a switch to an older branch, a rewritten branch) waits until it does instead of downgrading. `install.sh daemon-env list | set NAME... | unset NAME...` keeps settings for Swarm itself, such as the `TWITTER_*` credentials approved X posts use, in a root-only file the daemon unit loads; values are read from stdin, validated and never printed, and one restart applies them. Docs impact: `containers/headless/app/README.md` documents channels, the forward-only update and daemon settings.
- The headless installer gains `install.sh dev-sync /path/to/checkout`: it builds and applies the committed HEAD of a local Swarm checkout on the machine, so a change can be tested without pushing a branch, and the update timer stops following the GitHub branch until `install.sh dev-sync off`. Docs impact: `containers/headless/app/README.md` describes dev-sync.
- Headless setup no longer strands an owner on the models step: the SDK's `settings.restoreDefaults()` restores from revision 0 when the account has no model settings yet instead of throwing the read's 404, and "Use recommended models" (`POST /v1/agent-model-settings/restore-defaults`) now sets up the recommended models from the first ready provider when the account has no model settings yet (a key saved without the verification that normally creates them), and otherwise says a provider must be connected first, instead of answering "agent model settings not found". The setup app counts the provider step done only once a provider works, not once any key is saved, and finished steps can be reopened from the progress bar. The setup page shows which providers are connected. Docs impact: none.
- Headless machines can be watched from outside: the scoped-token listener (and so the tailnet AI gateway) now serves `GET /v3/box/summary`, `GET /v3/signals` and `POST /v3/signals` to keys holding `signals:read` or `signals:write`; signal sinks stay owner-only and client app and AI keys are still refused. `swarmctl setup sdk-token --monitor` mints a read-only monitoring key (`signals:read` only, up to 365 days). Docs impact: `containers/headless/app/README.md` describes monitor keys.

- Machine signal feed (`/v3/signals`, SDK `client.signals`). One durable, numbered feed per machine of high-level events for monitors, alert forwarders and AIs to follow with a cursor. Each signal has a dotted kind, a severity (info, warning, critical), short ids and a one-line summary; transcripts, command arguments and secret values never go in. Readers need `signals:read` and see their own account's signals plus machine-wide ones; the feed keeps the newest 50,000 and reports a `gap` when signals after a reader's cursor were dropped. Swarm raises its own signals: `agent.blocked` and `agent.unblocked` (an agent waits on an approval, a question or a plan, then moves on); `worker.run.succeeded`, `.failed` and `.cancelled`; `token.minted`, `.revoked`, `.deleted` and `token.denied` (a revoked or expired key, or one whose issuing key is gone, was presented; at most once per key per 10 minutes); `secret.used` (at most hourly per secret and website) and `egress.refused` (a sandbox was refused a private, local or metadata destination); `daemon.started`; and `sandbox.active` or `sandbox.inactive`. Ids, names and counts only.
