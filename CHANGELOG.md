# Changelog

All notable Swarm release changes should be recorded here.

Release entries are the source checkpoint for public docs verification. Each entry must include a `Docs impact` section. If a release has no docs-impacting changes, write `Docs impact: none`.

## Unreleased

- Long task messages can now be read in full: `read_task_session` returns a continuation offset instead of cutting them off. Before, `manage_projects` `read_task_session` (linked machines, max 20,000 characters) returned a longer message cut with `"truncated": true` and no way to read the rest, so an Orchestrator could report from half of a long final report. Now a cut message also carries `content_offset` (the UTF-8 byte offset where the returned part ends), `total_bytes` and `next`, the exact arguments for the following chunk: `message_id`, `message_seq` and `content_offset` (with `max_chars`). That read returns the next chunk of that exact message, marked with `content_start`. Chunks are cut on character boundaries and concatenate to the message exactly. A stale, misaligned or invented continuation is refused. The same parameters work on `GET /v3/fleet/linked-tasks/session` and through the linked-machine read, since the native action calls the same service function. `manage-sessions` `read_messages` had the same silent cut, without even a flag. It now uses the same rule (`tool.ChunkMessageContent`) and the same parameters. A message its content budget leaves out is reported (`budget_exhausted`, `has_more_newer`) instead of being skipped by `next_after_seq`. `get_task`'s compact `result` and `wait_tasks` outcome rows still show a shortened report, but now say so with `result_truncated`, `result_bytes` (the full size) and `read_full` (which read returns all of it). Short messages and reports are unchanged. Over MCP, `swarm_get_session` showed a long message cut with only `… [truncated N characters]`. Now a cut message carries `truncated`, `content_offset`, `total_bytes` and `next`, and `message_id`, `message_seq` and `content_offset` from `next` return its following chunk. That chunk comes from one HTTP route, `GET /v3/sessions/{id}/messages?message_id=&message_seq=&content_offset=[&max_chars=]`, with the same rule; Swarm Control may now call that route. The linked `get_task_session` view marks its cuts the same way and points to `read_task_session`. `swarm_task_result` now flags a shortened report with `result_truncated`, `result_bytes` and `read_full`. Tests: `TestChunkMessageContentReadsALongMessageExactly` and `TestMessageContinuationFromArgsRefusesPartialRequests` (tool) cover a ~50,000-byte message with multi-byte characters across chunk boundaries. `TestFleetLinkedTaskSessionReadsALongMessageInFull` (api, two in-process daemons over the real link, native action and HTTP route) and `TestManageSessionsReadMessagesPagesALongMessage` (api) also cover it. `TestControlMCPReadsALongTaskMessageInFull` (api) reads the ~50,000-byte report in full over the MCP tools and checks the `swarm_task_result` flag. `TestCompactProjectTaskFlagsAShortenedResult` (tool) and `TestProjectTaskWaitSummaryFlagsAShortenedResult` (pebble) cover the flags. Docs impact: docs/frontends.md (reading a long message in chunks).
- The stall check leaves old work alone, and old failed worker runs are no longer re-announced. Before, the first stall sweep on a forge picked up weeks-old tasks: mirrors of a retired Coder worker's runs, and old test tasks. Its "recovery" re-ran those old worker runs, and they failed at once. It then raised about 25 `task.stalled` warnings in 3 minutes, and the tasks read `needs_you`. Now the check skips a task whose last change is older than `stall_horizon_hours` (a new limit next to `stall_after_minutes`; default 24). It also skips archived tasks, and worker-run mirrors whose worker is gone, archived or not active. It never re-runs a worker's run as a recovery. On its first sweep after a start, a daemon sends at most one `task.stall_check_skipped` summary for that old work. Separately, three old failed Reviewer runs were re-announced as `job.failed` in the activity feed (two events about every 32 minutes, all night) with no new run. Each retry of their checkout cleanup re-saved the failed run twice, and every save of a failed run was labelled `job.failed`. Now a re-save of a run that keeps its final status (cleanup bookkeeping, a sandbox cleanup error) adds no activity entry. The cleanup retry stops after 5 attempts and raises one `job.cleanup_failed` warning. Docs impact: docs/task-progress.md (Stalled tasks: horizon, legacy work, summary signal).
- The agents-at-work read is fast again on a machine with many finished tasks. On the deploy server, with no agents running and no linked machines, `GET /v3/fleet/agents` (Swarm Control's `swarm_agents_at_work`, the console's bottom row and `/live`) took 28-30 s, with or without `machine` set to itself. The running agents were never the cost: they already come from the execution leases (`HeldRuns`, the set `running_now` counts). The time went to the finished-task summary (the recent list and today's landed and failed counts). On every poll it read each project's tasks with `ListProjectTasks`, which hydrates every record before applying its limit. Hydration reads the task's session, run state, terminal event and, for a planned worker run, its plan document twice. A machine whose scheduled workers (catalog refresh) leave thousands of finished planned runs read most of its store on each poll. That limit also kept the 1000 oldest-created tasks of a project, so on a large project today's finished tasks were never listed or counted. Now `localAgentsFinished` reads the stored task records without hydration (`ListProjectTaskRecordsForList`; task progress needs none of the hydrated fields). It sorts the finished tasks by their last change, computes progress only for the 8 shown and those that ended today, and keeps the result for 5 s per account, machine and `since` (`fleetAgentsFinishedTTL`), so clients polling every few seconds share one read. The response shape is unchanged. Test: `TestFleetAgentsStaysFastOnAStoreOfFinishedWorkerRuns` (api, real Pebble store with 3000 finished planned worker runs, each bound to a 16 KiB plan, and no active runs). The cold read answers within a generous 2 s bound (about 0.13 s here and about 1 s under `-race`, against 1.06 s without `-race` before the change on the same store). It reads task progress exactly once for each of the 10 tasks that ended today, never once per stored task. There are no agents. Today's failures are counted and the newest task is listed first (before the change: 0 failures counted and the list started at the 1000th-oldest task). A repeat read within the TTL makes no progress reads and returns the kept summary; after the TTL, a newly failed task is counted and listed first. Docs impact: none (response shape and documented behaviour unchanged; the finished-task summary may lag by up to 5 s).
- Delegated work no longer stalls silently. Before, a task could stop moving and still read "running" or "needs review" everywhere, with no alert and no wake for the Orchestrator that delegated it. On one forge afternoon this happened six different ways, and each was found an hour or more late. Now swarmd checks every unarchived agent task once a minute (`Server.RunTaskStallDetector`). The check reads only Swarm's own records and never calls a provider. A task is stalled when it is unfinished with no active run, queued run, workflow step or armed wait, and nothing changed for `stall_after_minutes` (new limit, default 20). A task is also stalled when an active run has had no event for `run_silent_minutes` (default 30) while not on a tool, a background command or an approval. A `wait_tasks` watch, a running background command, a running or waiting workflow step and a provider-limit wait (until its reset plus `stall_after_minutes`) are not stalls. Two shapes recover by themselves, each once. A review loop that used its rounds while the reviewer still blocks gets the findings as one extra turn in the task's session, then a handoff to the delegator. A run that ended with uncommitted changes and nothing committed gets one commit nudge per head. Every other stall, and a recovery that did not work, raises one `task.stalled` warning signal per task and stall episode. Its summary names the task, the machine and the state: approval (which tool), held by a drain or admission, provider limit until T, review exhausted, ended uncommitted, no run and no next step, or a silent run. The signal reaches swarm-watch through the signal feed. The same text wakes the delegating Orchestrator conversation through its session messages route. `task_state_reason` reads `stalled: …` on local, MCP and linked task reads. `task.unstalled` (info) follows when the task moves. The alert, wake and recoveries are keyed durably by episode, so a restart sends nothing twice. Tests (api, in-process daemon over a real Pebble store, executor off so no provider is reached): `TestTaskStallNoNextStepAlertsOnceWakesDelegatorAndUnstalls`, `TestTaskStallArmedWaitsAreNotStalled`, `TestTaskStallReviewExhaustedExtraRoundThenHandoff`, `TestTaskStallEndedUncommittedNudgesOncePerHead` and `TestTaskStallReasonReachesLinkedTaskList`. Docs impact: docs/task-progress.md (Stalled tasks), docs/automations.md (Signals: exhausted review loops), docs/box-limits.md (`stall_after_minutes`, `run_silent_minutes`).
- Automatic headless updates drain only an idle machine again. Before, the timer's update (`install.sh update --automatic`) drained a busy machine once updates had waited `UPDATE_BUSY_WAIT_SECONDS` (30 min) on it. That rule was added after the idle-only rule. On a forge the timer said "busy (3 running)" at 14:05, then at 14:11 drained with 6 runs going. The drain held every new run for 30 minutes, including a review loop's reviewer steps, so finished work could not be reviewed or pushed. When the operator cancelled the drain, the update exited 1. The timer (`OnUnitActiveSec`, already past due) ran it again at once, and the busy wait, which a cancel did not reset, drained again. Now `finish_update --automatic` never requests a drain while `GET /v3/box/busy` says busy, however long the machine stays busy: it records `waiting` and exits 0. `UPDATE_BUSY_WAIT_SECONDS`, `UPDATE_BUSY_DRAIN_SECONDS` and `update-busy-since` are removed. Its drain request carries `"if_idle": true`. swarmd (`executioncapacity.Manager.BeginDrainIf`) then checks the busy count under the admission lock and answers 409 with the counts instead of draining, so a run admitted after the installer's own check cannot slip in. A drain that ends without a switch leaves an automatic update `waiting` with exit 0 instead of failing: cancelled, replaced, timed out, refused, or its status unavailable. The update timer now uses `OnUnitInactiveSec=5min`, so the next run starts 5 minutes after the last one ended. `GET /v3/box/busy` adds `queued`: sessions with a run waiting for admission, for capacity or behind a drain, which a drain would hold. These count as busy, but not against `restart_resumable`. A person's `install.sh update` still drains a busy machine and waits. Tests: `install-update.test.sh` covers these cases. Two hours of busy timer runs with a 2-hour-old busy wait recorded never drain. Queued runs are busy. A 409 refusal waits with exit 0, and a person's update does not send `if_idle`. A cancelled drain waits with exit 0, and the next busy run does not drain. `install-release.test.sh` checks the timer's `OnUnitInactiveSec`. In Go: `TestBoxDrainIfIdleNeverFencesBusyMachine` (api) checks that a held lease plus a queued run gives 409 with the counts and no fence. On an idle machine it drains, a run held by the drain counts as queued, and a second if_idle request joins the drain. `TestBeginDrainIfChecksUnderAdmissionLock` (executioncapacity) is the other Go test. Docs impact: containers/headless/app/README.md (Updates; Update admission drain).
- Media generated in a conversation now shows there as a card, in Swarm Console and in the web chat. Before, the person saw only a tool line and had to find the result on the Media page. A finished `manage_media` `generate` or `retry` call (its `job_id` names the project media task, `media/PROJECT/TASK`), or a `manage_projects` `create_task`/`propose_task` for the image, video or sound agent, gets a card under it with the title and *generating*, *ready* or *failed*, then the image, the video's poster or the sound's player row. Clicking opens the existing viewer: in the console, the Media page's preview (the image large, video and sound in your player); on the web, the media viewer. The card holds only the task id and reads the job's state and files from the one record both clients already have (the console's Media list, the web's project task runtime), so it updates live and is the same after a reload; a linked machine's call gets no card. In the console, a media task that ended without a file now stays in the Media list as one failed record with its reason, for the card only; the Media page, its count and the conversation's media bar leave it out. On the web, the mapping from a task deliverable to the media viewer's item moved from `OrchestrateView.tsx` to `orchestrate/deliverable-media-item.ts`, shared with the chat card. The daemon is unchanged. Tests: console `a_media_call_becomes_a_card_linked_to_its_job` (map), `a_finished_media_call_gets_its_card_once` (live), `a_task_without_a_file_is_failed` and `an_accepted_task_keeps_its_files` (media); web `manage-media-job.spec.ts`, `manage-media-job-card.spec.tsx`. Docs impact: console/README.md (Media cards), docs/manage-media.md (showing a job in its conversation).
- Tool results an agent reads are now capped, and `webfetch` honours its character limit. Before, `bash` gave the model up to 4 MiB of command output, so a full package test run was fed back on every later turn: a read-only finder task on a low-cost model cost about $6.66 for a short task. Also, `webfetch` with `text: {maxCharacters: 300}` returned a whole ~22 KB page, because only the snake_case `max_characters` was read and Exa's own `maxCharacters` spelling was silently dropped. Now one startup setting, `tool_output_cap_bytes` (`0` = default 32768; otherwise 4096 to 1048576; an invalid value stops startup), bounds each result. Over the cap, `bash` keeps the head and tail of the output around `[N bytes omitted; full output saved to <path>; read it with read/search]`. This covers foreground results, a command moved to the background at its limit, `command: "status"`, and the report a background command adds to its conversation when it ends (that report was a fixed 4 KiB tail before). The result carries `output_capped`, `output_original_bytes`, `output_omitted_bytes` and `full_output_path`, or `full_output_error`. Full output is saved under `.swarm/tool-output/` in the workspace (files mode 0600, newest 50 kept, a self-ignoring `.gitignore` so it is never committed). Every mkdir, create, list and remove goes through `os.Root` handles whose names are checked to be real directories, so a directory an agent swaps for a symlink, before or during the save, cannot redirect the write or pruning outside the workspace; a swap during the save fails the save. Managed-execution `bash` output over the cap is not saved on the host (the lease's `read` could not reach it); its marker says the full output is unavailable. The in-memory capture now keeps the end of output past 4 MiB. `read` without `max_lines` stops at the last whole line within the cap and returns `next_line_start` (an explicit `max_lines` is unchanged). `search` keeps the leading results that fit, with `output_omitted_results` and the full answer saved. `webfetch` and `websearch` contents accept `maxCharacters` (and the other camelCase text/highlights options) as well as `max_characters`; different values in both spellings are refused. The limit is sent to Exa and applied again to the returned text (`text_truncated`), and without one each page gets an equal share of the cap (at least 1000 characters). Not changed: the run-level 128 KiB backstop for provider input, and `get_task` does not yet show the task's cost. The task session's recorded usage and `estimated_cost_usd` are readable with `manage_sessions`; wiring it into `get_task` touches `runtime_manage_project_tasks.go`, which another change owns. Tests: `TestBashOutputOverCapKeepsHeadTailAndSavesFullOutput`, `TestBashSmallOutputUnchanged`, `TestBashCaptureKeepsRealTailPastViewerBuffer`, `TestCapToolOutputRefusesSymlinkedOutputDirectory`, `TestSaveToolOutputSurvivesDirectorySwappedForSymlink`, `TestManagedBashCappedOutputNotSavedOnHost`, `TestCapToolOutputKeepsUTF8AndPrunesOldOutputs`, `TestToolOutputCapSettingDefaultAndBounds`, `TestReadWithoutMaxLinesStopsAtCap`, `TestEncodeCappedResultsPayloadDropsTrailingResultsAndSaves`, `TestWebFetchHonoursMaxCharacters`, `TestWebFetchDefaultPerURLCap` and the updated `TestBackgroundBashOutputKeepsTailAndMarksTruncated` (tool); `TestToolOutputCapConfig` (startupconfig). Docs impact: docs/agent-tools.md (Native agent tools: tool output cap; background report bound).
- A home now sees why a task it sent to a linked machine is stalled, and can answer its approval in the chat. Seen live: three tasks read `in_progress` for an hour while the machine's update drain held them and then while each waited on a bash approval. The machine's own `GET /v3/box/status` said "agents are waiting on a person", but the home's `list_tasks`/`get_task` did not, and the Orchestrator guessed "probably hit the usage limit" and could not answer. (1) The task-state projection now reads a working run's live records on its machine (`progress.live`; one rule, `pebblestore.ProjectTaskStateLive`/`ProjectTaskBucketLive`, used by local `list_tasks`/`get_task`, the task routes and MCP, the list counts and the Orchestrator's prompt block). A pending permission or question makes the task `needs_you` with `task_state_reason` `waiting for approval (permission <id>): bash: <command>` (or `waiting for an answer …` for `ask_user`) and the request (`permission_id`, `session_id`, `kind`, `tool`, `summary`); a client tool's pending call does not count. A run held by an update drain reads `waiting`, `held: update drain since <time>`; one in the admission queue reads `held: execution admission (…)`. (2) A linked machine's `list_tasks` and `get_task` carry its `task_state`, reason and `pending_request` through unchanged instead of recomputing them from the record, and `list_machines` gives each machine whose linked work rule is not off a one-line `status` from its `GET /v3/box/summary` (running, draining since, update state, sessions waiting on a person). (3) A wait on a linked task wakes when its run starts waiting on a person: the session's `permission.summary.updated` now reaches the activity feed as metadata (`state: needs_you`, no request text), so the home's watcher reads the task again without polling, and the outcome row carries `task_state`, `task_state_reason` and `pending_request`. (4) New `manage_projects action=resolve_task_permission` (`project_id`, `task_id`, `permission_id`, `decision` `approve`/`deny`, `reason`; the brief's `action approve|deny` is named `decision` because `action` is the tool's action): with `machine` it calls the machine's own `POST /v3/sessions/{id}/permissions/{pid}/resolve` over the link, only for a task this home sent there, only in the session the machine reports for that task, and only for a permission pending in it; `linked.{name}.work` `off` refuses, `ask` asks the person in the conversation, `auto` runs. Without `machine` it answers a request of the home's own task through the same permission service calls, under `Start tasks`. Each answer is allow once or deny once. The Orchestrator prompt says to tell the person what is asked and answer only on their word or under a rule that allows it; the `manage_projects` description says the same. The Orchestrator tool budget is now 35.5 KB (documented in its test). New `manage_projects` reads with `machine`, each a thin mapping over the machine's own route through the link and built by the same view functions as MCP (`controlMCPSessionStateView` and `controlMCPSignalPage`, factored out of MCP `get_session`/`activity` unchanged): `machine_status` (`GET /v3/box/summary`, the `swarm_status` data: attention and blocked sessions, drain and update state with times, running_now, usage against the cap, keys, sandbox), `get_task_session` (`GET /v3/sessions/{id}` for the session the machine reports for a task this home sent: active run, pending permissions and questions, latest messages trimmed, plan, `last_activity_at`; a task this home did not send is refused) and `activity` (`since_cursor`: one `GET /v3/activity` page; without it: `GET /v3/signals` with drains, refused keys and job failures). They run whenever the linked work rule is not off. The Orchestrator prompt adds: when a linked task looks stalled, read `machine_status` and `get_task_session` before saying why; never guess a cause. - A project task whose run ends on a provider usage limit now waits and continues by itself instead of failing. Before, a task run (`desktop-v3-run:task-…`, or a follow-up in the task's session) that ended with `claude code turn failed: You've hit your session limit · resets 1:50pm (UTC)` failed the task mid-edit, and nothing resumed it after the reset. Now such a task gets the status `limit_waiting` (`task_state` `waiting`). Its `task_state_reason` names the provider and the reset time. The reset is read from the message when it states one ("resets 1:50pm (UTC)" waits until 13:51 UTC), else a backoff of 5 minutes doubling to an hour. The record carries `limit_waits`, `limit_at`, `limit_retry_at`, `limit_run_id` and `limit_reason`, and the wait counts as `waiting`, not `needs_attention`. One `task.limit_wait` signal (warning) is recorded per wait, and a continuation that hits the limit again does not record another. At the reset, the same task session continues in its retained worktree through one canonical message and run intent (`<run>.limit<n>`). The message tells the agent its run stopped on a usage limit at that time and to check `git status`, finish what it was doing and commit. Uncommitted edits stay in place. The continuation's commit also turns the task `in_progress` and ends the wait, and its end counts as the job end of the run it continues. The wait is durable: an index written with the task record re-arms it after a restart at its reset time, not at startup. After 12 waits (now one shared `providerlimit.MaxWaits`, also used by workflow steps and worker runs) the task fails with the providerlimit "still in effect after 12 waits" reason. `stop_task` or archiving the task (the HTTP route or the native `archive_task`; the archive commit itself ends the wait) cancels the wait (the task is `stopped`), and the person's own message in the task session continues it at once. Linked-machine `list_tasks` rows show the wait as `state` `waiting` with a `state_reason`. The task stall check treats the wait as armed until its reset plus `stall_after_minutes`. Reviewer tasks and worker jobs keep their existing limit handling. Tests: `TestProjectTaskProviderLimitWaitsAndContinuesInItsSession` (the real V3 executor and a fake provider returning the Claude Code session-limit text: parsed reset, task state, one signal, nothing before the reset, a second wait without a second signal, the continuation note reaching the provider in the same session, an uncommitted file kept, `needs_review` at the end), `TestProjectTaskProviderLimitWaitIsBounded`, `TestProjectTaskProviderLimitWaitStopAndArchiveCancel` (stop, archive and the person's message), `TestProjectTaskProviderLimitWaitNativeArchiveCancels`, `TestProjectTaskProviderLimitWaitSurvivesRestart`, `TestTaskStallProjectTaskLimitWaitIsArmed` (api); `TestProjectTaskLimitWaitingState`, `TestProjectTaskLimitRunIDs`, `TestProjectTaskLimitWaitIndex` (pebble). Docs impact: docs/task-progress.md (the `waiting` state, the new "Waiting for a provider's usage limit" section), docs/automations.md (project task runs wait like worker jobs).
- A home can now read and change a linked machine's folder environments (the image, setup commands, env and `max_leases` a folder's sandbox and leases run in) through the link, without SSH. Before, the only route was root SSH to the machine: the link proxy reached `/v1/environments`, which belongs to deployment environments and refused the home ("environment access denied"), and no tool covered folder environments for a linked machine or for the home's Orchestrator. The Orchestrator's `manage_projects` has four new actions: `list_environments`, `get_environment`, `update_environment` and `rebuild_environment`. The last three take `workspace_path`, and all four take `machine` for a linked machine. `update_environment` merges, with its fields in the `environment` object: `append_setup` adds commands, `setup` replaces them, `env` sets variables, `unset_env` removes them, `base_image` and `max_leases` set theirs, and fields left out are kept. `wait_seconds` waits up to 110 seconds for the build. Linked calls go to the machine's `/v3/sandbox-environments` route (new: `GET /list`, merge `PATCH`, `POST /rebuild`). That route and local calls use the same service functions in `sandbox_environments.go`, and `PUT` keeps its full-replacement behavior. The home's `linked.{name}.work` rule gates every call. `off` refuses. `ask` waits for the person before `update_environment` or `rebuild_environment`, because they run setup commands on the machine. `auto` runs every call. Secret grants and permission rules are not part of an environment. `secrets`, `secret_grants`, `grants`, `permissions` and similar fields are refused by name, on the home and again on the machine (HTTP 403 over the link), and nothing is stored. Environment views carry no secret names or values. Task sessions are refused and use `lease_environment`. A failed build returns its error and build log tail. A machine that does not answer is now reported as "could not reach linked machine NAME: NAME unreachable, the call failed at TIME; last successful contact at TIME", without the machine's address. This applies to linked environment, project and task-session reads. MCP's `swarm_set_environment` gains `append_setup` and `unset_env` (the same merge) and `rebuild`. The Orchestrator prompt lists the actions. To stay within the Orchestrator tool budget, the update fields share one schema property (tools 35,751 of 35,840 bytes). Tests: `TestHomeManagesLinkedFolderEnvironment`, `TestLinkedFolderEnvironmentAccessAndSecretRules`, `TestFolderEnvironmentRefusalsStayAndUnreachableIsNamed` and `TestManageProjectsEnvironmentActionsLocalAndLinked` (api; two in-process daemons over the real pinned link, with a test double only for the Docker build); `TestFolderEnvironmentActionsAndArguments` (tool); `TestSandboxEnvironmentListAndRebuild` (pebble). Docs impact: docs/access-model.md (folder environments over the link, what the home may not change, `ask` before environment changes), docs/checkpoints/swarm-control.md (`swarm_set_environment` arguments), the `manage_projects` and `swarm_set_environment` tool descriptions, and the Orchestrator prompt (swarmd/internal/agent/system_agent_registry.go).
- Swarm Console shows how many agents run across the fleet and what each is doing. Before, the only view was the Live page's raw event stream, one line per event. (1) The daemon has one new read, `GET /v3/fleet/agents` (`FleetAgents`, `swarmd/internal/api/fleet_agents.go`). No existing route answered which runs are active now with what each does: `swarm_status` and `running_now` only count, `swarm_list_runs` lists worker runs on one machine, and the fleet activity is a feed of events. A run is listed while it holds an execution lease, the same set `running_now` counts (new `executioncapacity.Manager.HeldRuns`, which also names each lease's account). Each run gives its machine, agent, session and run ids, task id and title when it is a task's, start time, and last tool call: kind, tool, and a one-line target such as a path or a command's first line. It also gives a timeline of the last 12 calls, counts of reads, edits, commands, commits and calls in the last minute, and the files edited. When a workflow takes the task, it gives the workflow step (`code`, `review`, `fix` with its round, `push` or `landed`), read from the task's `progress`. The code step is shown only when an enabled workflow would apply at the job's end (`Automation.Matches`). The answer also has each machine's agent count and today's landed and failed tasks, the latest 8 finished tasks with their derived state, and totals. Linked machines are read in parallel through the existing link (`scope=machine` on their own route, 5 s each), only while `linked.{name}.work` is `ask` or `auto`.
