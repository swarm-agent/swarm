- A folder's jobs can be delivered as pull requests instead of a local merge. On the headless box the administrator runs `swarmctl workspace publish PATH COMMAND [--auto]` (root; `--off` goes back to merging): the rule lives in the root-owned `/var/lib/swarm-headless/publish`, which the daemon reads (`SWARM_PUBLISH_CONFIG`) and refuses unless root owns it and only root can write it, like the command. `swarm_deliver_job` on a job in that folder then runs COMMAND on the host as Swarm's user (never in a sandbox; agents never see it or its credentials), with `SWARM_PUBLISH_FOLDER`, `_JOB_ID`, `_BRANCH`, `_HEAD`, `_BASE_BRANCH`, `_TITLE` and `_BODY_FILE` (the job's report), a five-minute limit and a minimal environment; the command's last output line is the pull request URL, recorded on the job's task (`integration.state` `pull_request`, `pull_request_url`) and in the feed as `job.pull_request`. A failure is `job.publish_failed`. With `--auto` the daemon delivers each finished worker job with commits in that folder without anyone calling `swarm_deliver_job` (it waits for the job's commits to be assessed, retries for about an hour, then records `job.publish_failed`); jobs that ended before publishing was set up are not delivered. Swarm ships `containers/headless/app/publish-github.sh`, a COMMAND for GitHub: it pushes the job's exact head to `ai/swarm-<job hash>` and opens or updates its pull request as a GitHub App installed on that one repository (settings in a root-owned file next to it), with the token only in the environment and on curl's stdin, and with `AUTO_MERGE=on` turns on GitHub's auto-merge so the repository's required checks decide; `publish-github.test.sh` tests it against a fake API and a local repository. Merging is never done by Swarm. Docs impact: installer usage (`swarmctl workspace publish`).
- `publish-github.sh` gives repository hooks a private scratch folder (`TMPDIR`) when Swarm runs it without one, and takes `PUSH_HOOKS=off` in its settings to skip the folder's own git hooks for its push only, for a repository whose pre-push hook runs a gate (for example a container test Swarm's locked-down user cannot run) that the base branch already requires as a check before merging; the default stays `on`, and the test proves a failing pre-push hook blocks the push unless it is off. Docs impact: none.
- A folder that publishes as pull requests can keep up with its forge: `swarmctl workspace publish PATH COMMAND [--auto] [--sync]` (the rule's third field is now a comma list, `auto,sync`). With `--sync`, before each worker job in the folder the daemon runs COMMAND with `SWARM_PUBLISH_ACTION=update` (and the folder's branch in `SWARM_PUBLISH_BASE_BRANCH`); it fetches the forge's base branch into the folder and prints `COMMIT BRANCH`, and the job starts from that commit with that branch as its base, so a pull request merged on the forge yesterday is today's starting point instead of a stale local branch that would make the next pull request conflict. When the update fails the job does not start and the next reconcile fails the run with the reason (`worker.run.failed`). Every publish command now runs with its own scratch folder as `TMPDIR` and gets `SWARM_PUBLISH_ACTION` (`publish` or `update`). `publish-github.sh` implements the update with a read-only App token (fetching into `refs/swarm/publish/BRANCH`, never touching the owner's checkout) and fails a delivery whose pull request conflicts with its base, naming it, so it is reported instead of waiting forever. Docs impact: installer usage (`swarmctl workspace publish --sync`).
- A job's result reads its head from the job's own worktree when the delivery assessment cannot (the assessment needs the folder to have the job's base branch checked out, which a `--sync` job's forge base never is), so such a job is still published as a pull request instead of being skipped for having no head.
