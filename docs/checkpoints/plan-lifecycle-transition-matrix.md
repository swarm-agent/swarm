# Canonical plan lifecycle transition matrix

This matrix defines the public AI/API operation for each plan-definition intent. Approval is the authorization boundary: an approved operation applies the definition change and selects the next runnable checkpoint immediately when the effective policy is automatic and no review/block/failure gate remains.

| User intent | Canonical operation | Required source state | State preserved | State reset/applied | Expected outcome after approval | Invalid/ambiguous alternatives |
| --- | --- | --- | --- | --- | --- | --- |
| Propose a genuinely separate plan | `request_new_plan` without `plan_id` | Any session state in which a new proposal may be reviewed; complete structured document required | Existing active plan remains active until approval | Proposed checkpoints are reset to `pending`; stale run/attempt state is discarded | Approved proposal becomes the active approved plan and its first checkpoint is returned/queued for fresh-context execution when automatic policy permits | `new`, `save`, or a title/markdown-only proposal cannot create the executable plan |
| Amend the current plan's future definition | `amend_plan` with `base_revision` and either `replace_from_checkpoint_id` or `amend_future_checkpoints=true` | Approved active plan; base revision must match unless explicit stale override is approved | Completed checkpoints and the current in-progress/waiting-review checkpoint, including attempts and evidence | Replaced/new future checkpoints are reset to `pending`; completed-plan append clears only obsolete final-review execution state under automatic policy | First amended/appended future checkpoint becomes the selected runnable checkpoint when automatic policy permits; current in-progress work remains current | The retired `request_plan_revision`, legacy full `save`, and generic whole-document patching are not valid for this intent |
| Replace the entire current plan with a new definition | `request_new_plan` with the current `plan_id` | Existing target plan; complete structured replacement and approval required | Plan identity only | All replacement checkpoint runtime/attempt state is reset; old definition/history remains in revisions | Replacement is saved approved and active, and its first checkpoint is returned/queued for fresh-context execution when automatic policy permits | `new override=true`, `save`, and `request_plan_revision` are rejected as competing replacement paths |
| Append one requested ordered checkpoint | `request_followup_checkpoint` | Approved active plan; non-empty verbatim `change_request`; parent conversation owns creation | Completed/current history and later pending work | Exactly one new pending checkpoint is inserted at the current lifecycle boundary; blocked/paused checkpoint is superseded only under the explicit follow-up rules | Auto-start policy returns/queues the inserted checkpoint; approval policy applies and then selects it; failed plans reject without mutation | `start_session_checkpoint` is only for no-active-plan bootstrap; checkpoint runs cannot recursively append |

## Invariants

1. `request_plan_revision` is not a public mutation path. Callers must choose `amend_plan` for preserved-history future changes or `request_new_plan` with `plan_id` for full replacement.
2. Permission approval applies the approved canonical arguments once. It must not create a second pending plan approval.
3. Definition approval never trusts caller-supplied runtime state. New/replaced future checkpoints begin pending with empty run, attempt, report, result, and review state.
4. Completed/current state is immutable across `amend_plan`; stale revisions and attempts to replace protected checkpoints fail before persistence.
5. Automatic continuation returns or queues the selected checkpoint in the same lifecycle result. Manual review, blocked, paused, and failed gates stop clearly.
6. Legacy `new` is limited to an empty draft shell with no active plan. Legacy full `save` cannot replace an approved active structured plan.
