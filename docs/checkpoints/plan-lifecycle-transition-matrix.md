# Canonical plan lifecycle transition matrix

This matrix defines the public AI/API operation for plan-definition and active-feedback intents. Approval remains the authorization boundary for approval-bearing definition changes; guidance-only responses and localized `add_subtask` refinements do not require plan approval. Approved operations select the next runnable checkpoint immediately when the effective policy is automatic and no review/block/failure gate remains.

| User intent | Canonical operation | Required source state | State preserved | State reset/applied | Expected outcome / approval behavior | Invalid/ambiguous alternatives |
| --- | --- | --- | --- | --- | --- | --- |
| Ask a question or give guidance without implementation intent | Respond without plan mutation | Any active-plan state | Entire plan, checkpoint, attempt, and subtask state | Nothing | The user receives the answer or acknowledgment; execution state is unchanged | Imperative wording alone is not implementation intent, and a suggestion must not silently create work |
| Request a localized additive refinement to the current deliverable | `add_subtask` on the active checkpoint | Runnable active checkpoint whose objective and acceptance criteria remain valid; blocked and failed checkpoints must use their canonical recovery paths | Plan/checkpoint identity, objective, acceptance criteria, existing subtasks, attempt history, and valid completed work | The new subtask is appended; a completed/review checkpoint may reopen in place, but no checkpoint or attempt is created/reset | Work continues in the same checkpoint/run boundary; for example, replace a sentence, change a button color, or add local spacing | `restart_checkpoint` is too disruptive when the contract remains valid; `request_followup_checkpoint` is for independent work; `add_subtask` cannot clear blocked/failed state |
| Redefine the current checkpoint contract | `restart_checkpoint` with `change_request` and complete replacement definition | Non-blocked checkpoint whose objective or acceptance criteria are invalidated; complete replacement title/tasks/acceptance criteria/notes required | Checkpoint identity and durable prior history according to the restart contract | Current runtime execution is reset and the replacement definition starts in fresh context | The same deliverable is retried against the materially replaced contract | Do not restart merely because feedback is phrased as a command or adds a bounded edit |
| Propose a genuinely separate plan | `request_new_plan` without `plan_id` | Any session state in which a new proposal may be reviewed; complete structured document required | Existing active plan remains active until approval | Proposed checkpoints are reset to `pending`; stale run/attempt state is discarded | Approved proposal becomes the active approved plan and its first checkpoint is returned/queued for fresh-context execution when automatic policy permits | `new`, `save`, or a title/markdown-only proposal cannot create the executable plan |
| Amend the current plan's future definition | `amend_plan` with `base_revision` and either `replace_from_checkpoint_id` or `amend_future_checkpoints=true` | Approved active plan; base revision must match unless explicit stale override is approved | Completed checkpoints and the current in-progress/waiting-review checkpoint, including attempts and evidence | Replaced/new future checkpoints are reset to `pending`; completed-plan append clears only obsolete final-review execution state under automatic policy | First amended/appended future checkpoint becomes the selected runnable checkpoint when automatic policy permits; current in-progress work remains current | The retired `request_plan_revision`, legacy full `save`, and generic whole-document patching are not valid for this intent |
| Replace the entire current plan with a new definition | `request_new_plan` with the current `plan_id` | Existing target plan; complete structured replacement and approval required | Plan identity only | All replacement checkpoint runtime/attempt state is reset; old definition/history remains in revisions | Replacement is saved approved and active, and its first checkpoint is returned/queued for fresh-context execution when automatic policy permits | `new override=true`, `save`, and `request_plan_revision` are rejected as competing replacement paths |
| Request independently shippable work, a separate review/failure boundary, or another ordered checkpoint | `request_followup_checkpoint` | Approved active plan; non-empty verbatim `change_request`; parent conversation owns creation | Completed/current history and later pending work | Exactly one new pending checkpoint is inserted at the current lifecycle boundary; blocked/paused checkpoint is superseded only under the explicit follow-up rules | Auto-start policy returns/queues the inserted checkpoint; approval policy applies and then selects it; failed plans reject without mutation | `start_session_checkpoint` is only for no-active-plan bootstrap; checkpoint runs cannot recursively append |

## Invariants

1. `request_plan_revision` is not a public mutation path. Callers must choose `amend_plan` for preserved-history future changes or `request_new_plan` with `plan_id` for full replacement.
2. Permission approval applies the approved canonical arguments once. It must not create a second pending plan approval.
3. Definition approval never trusts caller-supplied runtime state. New/replaced future checkpoints begin pending with empty run, attempt, report, result, and review state.
4. Completed/current state is immutable across `amend_plan`; stale revisions and attempts to replace protected checkpoints fail before persistence.
5. Automatic continuation returns or queues the selected checkpoint in the same lifecycle result. Manual review, blocked, paused, and failed gates stop clearly.
6. Legacy `new` is limited to an empty draft shell with no active plan. Legacy full `save` cannot replace an approved active structured plan.
7. Feedback routing uses the least disruptive valid route and is based on contract impact: inquiry/guidance → no mutation; localized patch → `add_subtask`; checkpoint redefinition → `restart_checkpoint`; independent deliverable/review boundary → `request_followup_checkpoint`.
8. `add_subtask` preserves checkpoint identity and attempt history. It must not clear blocked or failed state; those states remain governed by explicit lifecycle recovery.
