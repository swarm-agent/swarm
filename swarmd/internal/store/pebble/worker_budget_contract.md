# Worker budget enforcement

Worker policies are account/worker-scoped and separate from AI-editable worker definitions. Numeric caps default to zero (unset). Only authenticated, unscoped user HTTP ingress may change the policy; PUT requires the exact policy revision. Updates do not change account limits, provider/model settings, usage receipts, or reservations.

Admission and every integrated provider/media boundary resolve worker ownership through the existing corroborated durable usage lineage. Account caps alone never classify ordinary sessions, tasks, Router calls, titles, or memory extraction as worker work. Non-worker operations neither read nor acquire worker-budget reservations; previously persisted account reservations cannot block them. Current UTC-day indexed receipt totals govern spending, not context occupancy. Catalog, provider and provider-estimate costs count once; nominal subscription-equivalent costs are not dollar charges. Unknown receipts block dollar-capped work. Legacy account accumulators without explicit pricing coverage remain incomplete across incremental receipts and block dollar-capped work; new receipts cannot certify old pricing.

For corroborated worker operations, a capped worker and an enabled capped account each reserve their remaining allowance exclusively for one billable operation, in one atomic batch under the account mutation lock. This intentionally serializes capped worker descendants and runs rather than guessing output/price ceilings. Reservations are durable and survive restart and UTC rollover. Exact local operation identities are recorded in canonical receipt batches. Only a terminated operation with that same receipt identity can release its reservation; corrections to older calls cannot settle new calls. Legacy unidentified reservations stay blocked; missing receipts do not trigger timed refunds. A daemon interruption can therefore require explicit accounting/recovery investigation before further capped work. No AI reset endpoint exists. GET returns indexed UTC-day policy/usage, nullable remaining amounts, worker/account worker-operation inflight and blocked state, coverage and limitations. Policy PUT commits a scoped durable `worker.updated` invalidation with `budget_revision`; consumers hydrate status on that event, not polling.

This is stop-before-next-call enforcement, **not an invoice-hard cap**. Already-dispatched work may exceed the remaining allowance before provider usage is returned. Late genuine canonical receipts remain counted irrespective of cancellation/failure. Transport that never supplies a receipt cannot be reported as measured zero.

Conservative limitations:

- Cost-capped media generation is rejected because the tool ingress currently lacks a dimension-specific verified pre-charge quote. Token-only policies use exact operation identities at the canonical media receipt boundary. Reservations now occur after service preflight/credential checks immediately before transport, so pre-dispatch validation failures do not strand allowance. Post-dispatch failures without receipts remain uncertain and block.
- Capped background titles, direct one-shot Designer generation, AI-task metadata preparation and session-bound memory extraction are rejected where their existing callers have no canonical receipt persistence boundary.
- Provider watchdog retries for capped workers stop and return available usage for settlement before any new attempt.
- The main provider watchdog retains a bounded five-minute post-return collector for genuine late responses; persistence failure or later/unavailable receipts leave reservations unresolved. V3 and Compact also retain bounded five-minute post-return collectors, using immutable per-attempt receipt identities; termination without usage retains uncertain allowance. This implementation does not add invoice reconciliation or recover provider usage that never reaches an existing receipt boundary. Source-backed tests require parent execution; no live qualification is claimed.

## Daily exhaustion holds

Policy PUT rejects a worker USD/token limit above the corresponding enabled finite account daily ceiling (HTTP 400), preserving revision and usage on rejection. Zero remains unset/inherit, never zero allowance. Lowering the account ceiling keeps the worker policy unchanged; effective enforcement remains the minimum.

GET adds `hold` (nullable/omitted), `reset_at` (next UTC midnight, Unix milliseconds), `effective_cost_limit_usd` and `effective_tokens_limit` (nullable when neither corresponding ceiling is set). A hold has `date`, `reason: daily_budget_exhausted`, `cap_source: worker|account`, `dimension: usd|tokens`, numeric `limit`/`usage`, and `reset_at`. It is independent of lifecycle/revision: policy changes cannot clear it within that day. Day-keyed holds expire by eligibility at UTC rollover, without changing manual pause/archive/pending/disabled state or refunding unresolved reservations. Old holds remain as durable deduplication evidence.

Receipt batches atomically persist worker exhaustion holds and account exhaustion holds for the bounded account worker catalog together with canonical notification records/indexes. Admission/pre-call checks are backstops for lowered limits or existing usage. Reservations, unknown pricing and incomplete coverage block operations but do not create exhaustion holds. Scheduler sweeps skip held workers; reconciliation cancels outstanding canonical worker intents through the existing lifecycle boundary, including admitted work not yet dispatched. Already dispatched provider calls may overshoot; genuine late receipts still count.

Initialized daemons use the canonical local node identity for one notification per worker/UTC day (`worker.budget.exhausted`, system/warning, payload `worker_id` and `budget_hold`); clearing the inbox does not recreate the alert. Receipt publication runs after releasing account locks and bridges the durable alert to the existing idempotent V3 `notification.resource.updated` path. UI consumers should hydrate worker budget status on this worker-scoped notification as well as existing `worker.updated` policy invalidations. Missing wakeups remain recoverable from the canonical notification inbox/bootstrap. Uninitialized stores without a local node retain holds but cannot address an inbox notification. No new invoice reconciliation, push delivery guarantee, or live qualification is claimed.
